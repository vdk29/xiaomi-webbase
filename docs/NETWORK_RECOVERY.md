# Восстановление загрузки каталога

На снимке пользователя: GET `/rest/v1/webbase_products`, `ERR_CONNECTION_RESET`
вместе с `200 (OK)` и `TypeError: Failed to fetch`. Это означает, что браузер
не смог получить ответ целиком, даже если HTTP-заголовки уже содержали 200.
По одному снимку нельзя определить, кто сбросил соединение: сеть, провайдер,
прокси, защитное ПО или серверный компонент.

На момент проверки Supabase Health вернул 200; в просмотренном журнале
запросы каталога возвращали 200 с максимальной обработкой 462 мс. Это не
доказывает исправность маршрута от конкретного компьютера пользователя.

Исправления интерфейса:

- Каталог запрашивает только нужные поля и до 50 товаров за запрос.
  Описания и полные характеристики загружаются при открытии карточки.
  В каталог передаётся только используемая часть `specs._compatibility`.
- Чтение каталога, профиля и карточки повторяется до трёх раз при транспортных
  сбоях, 429 или 5xx. Одна попытка ограничена 8 секундами и отменяется через
  AbortSignal; авторизационные и валидационные ошибки не повторяются.
- Получение общей галереи ограничено двумя попытками по 3 секунды. При сбое
  каталог остаётся доступным с собственными фотографиями и сообщением.
- Ошибка каталога не показывает форму входа для уже одобренного пользователя.
  Добавлены понятное сообщение и кнопка повторной загрузки. При неудачном
  обновлении ранее загруженные данные остаются с предупреждением об остатках.
- Одновременные запросы обновления каталога объединяются.
- Импорт, загрузка фото, сохранение товаров и управление сотрудниками не
  получают автоматических повторов: эти операции могут менять реальные данные.

Проверки: `npm test`, `npm run check`,
`scripts/verify-network-recovery.cjs` (Playwright, локальный сервер 4173,
`CHROMIUM_PATH` при необходимости). Браузерный тест воспроизводит отказ,
сохраняет вход, восстанавливает 51 товар через страницы после временного
сбоя и проверяет, что недоступность общей галереи не блокирует каталог.

Если сбросы повторяются после обновления страницы без кэша, сравните тот же
компьютер через другую сеть, например мобильную точку доступа. Это помогает
отличить проблему маршрута/фильтрации от ошибки приложения; защиту данных и
RLS отключать для такой проверки не требуется.

## Дополнительная оптимизация запуска

- Supabase JS 2.95.0 размещён в `vendor/` на том же сайте. SheetJS 0.18.5
  (882 КБ) загружается локально только при выборе Excel-файла. CDN не нужен
  для открытия входа или каталога; версии и лицензии сохранены.
- Первая порция из 50 товаров отображается до получения остальных страниц.
  Полный каталог читается с приоритетом категорий устройств. Индикатор явно
  показывает продолжающуюся загрузку. При обрыве остаётся предупреждение о
  неполном списке, а импорт заблокирован до полного чтения; при обновлении
  каталога старый предварительный расчёт импорта сбрасывается.
- Общая галерея запрашивается только для новых вариантов смартфонов/планшетов
  без фото и больше не блокирует показ каталога. Щётки, ремешки и другие
  неподходящие категории не создают пустых запросов этого RPC.
- Начальные события SDK и обновление токена не перезагружают весь каталог.
  Повторный SIGNED_IN проверяет профиль без повторного чтения уже готового
  каталога. Смена пользователя и выход очищают отображаемые данные.
- Кэш ссылок на фото использует текущий идентификатор сессии без повторного
  захвата SDK-lock для каждой картинки. Это идентификатор для изоляции кэша,
  а не проверка прав: доступ к данным по-прежнему контролирует Supabase/RLS.
- Проверка сессии ограничена 18 с, захват SDK-lock — 10 с, передача ответа
  Auth целиком — 12 с. Добавлена кнопка повторного подключения. Изменяющие
  данные операции по-прежнему не получают автоматических повторов.
- Если соединение оборвалось ещё при скачивании JavaScript, отдельный
  встроенный контроль запуска через 15 секунд показывает сообщение и кнопку
  повторного открытия. Он не зависит от загрузки основного модуля приложения.

Повторная диагностика: API каталога в среднем отвечал около 100 мс, запросы
PostgreSQL — обычно 5–9 мс. Блокирующих соединений, зависших транзакций и
deadlock не обнаружено. Это не подтверждает качество маршрута от компьютера
пользователя, но признаков перегрузки базы на момент проверки не было.

`scripts/verify-startup-performance.cjs` проверяет запуск при заблокированных
внешних доменах, настоящий локальный SDK с изолированными ответами Auth,
первую страницу при задержке следующих, блокировку импорта неполного списка,
фоновую галерею и отсутствие повторных запросов при событиях сессии.
Если доступен исходный файл пользователя (`WEBBASE_TEST_WORKBOOK`), тест
разбирает его в предпросмотре через лениво загруженный SheetJS без записи
в базу. Локальное время открытия входа в тесте — около 0,2 с; это измерение
на тестовом сервере, а не обещание времени загрузки через интернет пользователя.

## 25.10.2026: приоритет наличия и снижение числа запросов

После наполнения каталога до 494 товаров старый алгоритм выполнял 10
последовательных запросов по 50 строк и подписывал фотографии всего каталога,
включая невидимые карточки. При большом RTT это увеличивало время ожидания.
Наличие не участвовало в серверной сортировке.

Миграция `20261025095850_prioritize_available_catalog.sql` добавляет представление
`webbase_catalog` с `security_invoker=true`. Признак `catalog_in_stock` считается
из текущих `warehouse + display > 0`, без копии остатков и дополнительных
триггеров. ЛДУ отдельно не прибавляется: он уже входит в витрину. RLS исходных
таблиц сохраняется, anon не получает прав, authenticated получает только SELECT.
Связи фотографий и остатков доступны через прежний PostgREST select.

Каталог читает представление с сортировкой по наличию, категории, названию и UUID.
Первая порция — 50 строк, последующие — по 200; для 494 товаров это четыре
запроса. Интерфейс также сортирует наличие перед категорией, поэтому после
окончательной отрисовки товары с остатком остаются наверху. Приоритет действует
и внутри выбранной категории, порядок обновляется после изменений остатков.
Импорт остаётся заблокированным до полной загрузки всех товаров.

Убрана предварительная подпись фотографий всего каталога. Первые восемь и
видимые при прокрутке изображения получают ссылки пакетами, предзагрузка
IntersectionObserver уменьшена с 600 до 300 px. Подписанные ссылки по-прежнему
кэшируются на пользователя. Подписание имеет две попытки с ограничением по
5 секунд; SDK-fetch для `/storage/v1/object/sign/` прерывается через 6 секунд,
включая чтение тела ответа. Зависшая попытка не держит pending-кэш бесконечно.
Это ограничение не затрагивает загрузку файлов, импорт, изменение товаров и
сотрудников. Тайм-аут auth остаётся 12 секунд без автоматического повтора входа.

Диагностика существующего проекта: за доступные сутки успешные чтения товаров
в среднем 94,8 мс, максимум 831 мс; пакетное подписание — 131,4 мс в среднем,
максимум 1233 мс. Блокированных соединений нет. EXPLAIN ANALYZE новой первой
страницы с ролью authenticated и RLS: выполнение 9,13 мс, сортировка top-N,
40 КБ. Advisory по производительности — только прежние три неиспользованных
индекса; новые индексы для 494 строк не добавлялись. Эти измерения не измеряют
маршрут от конкретного Wi-Fi/оператора пользователя и не устанавливают причину
его сетевых обрывов.

Проверки: 50 Node-тестов; `tests/catalog-priority.sql` проверяет реальную
приоритизацию, реакцию на изменение остатка и права доступа, с откатом фикстуры.
`scripts/verify-stock-priority.cjs` использует настоящий локальный SDK и
изолированные ответы API: 494 товара, 202 с остатком, сетевой reset, первая
порция, импорт до завершения, поиск, четыре чтения и отсутствие массовой
подписи невидимых фото. Профили Chromium: Wi-Fi 70 мс / 1,5 МБ/с,
mobile 350 мс / 180 КБ/с, процессор замедлен в четыре раза. В локальной проверке
первые 50 появились примерно за 1,3/4,2 секунды с искусственным обрывом;
подписывалось 19–20 видимых фото, самый длинный CPU-task около 250 мс.
Это результаты эмуляции, а не обещание скорости на реальной сети пользователя.
Также повторно выполнены browser regressions старта, обрыва сети и возврата
в выбранную категорию. Скрипты поддерживают `CHROMIUM_PATH` и `WEBBASE_TEST_URL`.
